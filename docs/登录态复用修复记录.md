# 登录态复用修复记录

日期：2026-09-16

## 问题现象

小红书扫码登录成功后（页面已跳转首页/推荐流），点击「终止」退出，下次启动仍需重新扫码——登录态未被复用。

## 根因

**Chrome/Edge 的 cookie 是内存态，只有走正常退出流程才会写回 `Default\Network\Cookies`。原代码在收到终止信号时立即强杀浏览器，导致本次登录 cookie 丢失。**

具体链路（`tools/app_runner.py` 的 `_on_signal`）：

1. 收到 SIGINT/SIGTERM
2. `on_first_interrupt()` → `main.py` 的 `_force_stop()` → `launcher.cleanup()`
   → 原实现直接 `process.terminate()`（Windows 上是 `TerminateProcess`，等于强杀）
3. **浏览器在此刻被强杀，cookie 无法落盘**
4. 之后才走 `async_cleanup()` → `cdp_manager.cleanup(force=True)`，但为时已晚

## 修复内容（三处）

### 1. `tools/browser_launcher.py` — `cleanup()`

Windows 分支改为**先优雅关闭**：
- 先用不带 `/F` 的 `taskkill /PID <pid> /T`（向窗口发 `WM_CLOSE`，触发正常退出流程 flush cookie），等待最多 8 秒
- 仅当优雅关闭超时/失败时，才用 `taskkill /F /T /PID` 强制结束

### 2. `tools/cdp_browser.py` — `cleanup()`

在断开 CDP 连接**之前**，通过 CDP 主动发送 `Browser.close`：
```python
cdp_session = await self.browser.new_browser_cdp_session()
await cdp_session.send("Browser.close")
await asyncio.sleep(1.5)
```
- 这是触发 cookie 落盘的关键动作
- 仅当 `AUTO_CLOSE_BROWSER=True` 或 `force=True` 时执行
- `CDP_CONNECT_EXISTING=True`（连接用户已有浏览器）时跳过，不替用户关浏览器

### 3. `main.py` — `__main__` 中断钩子

移除原来在首次中断时立即强杀浏览器的 `_force_stop()`，改为 no-op 占位，
让 `async_cleanup()` 走完整优雅关闭链路。清理超时从 15s 提升到 30s。

## 验证

源码模式端到端测试（独立测试目录，未污染正式登录态）：
- 启动 CDP 浏览器 → 打开小红书 → 调用 `cleanup(force=True)`
- 日志出现 `Sent Browser.close via CDP (login state flushed)`
- 日志出现 `Browser process already exited, no cleanup needed`（浏览器自行优雅退出，未被强杀）
- `Default\Network\Cookies` 文件在 `Browser.close` 的同一秒被创建/更新（mtime 更新）
- **结论：修复前 cookie 永远丢失，修复后 cookie 成功落盘**

## 预期效果

修复后：
1. 扫码登录一次成功后，cookie 会正确落盘
2. 下次启动 `XiaoHongShuClient.pong()`（`query_self()` 校验）能通过 → 自动复用登录态，**免扫码直接开爬**
3. 仅在登录态真正失效时才需要重新扫码

# 后续修复记录（2026-09-16 晚）

## 问题一：数据管理预览崩溃（GUI 接口 500）

### 现象

打开「数据管理」预览采集到的 Excel 时，后端接口 500，`server.log` 反复出现：
```
ValueError: Out of range float values are not JSON compliant
  File "starlette\responses.py", line 187, in render
  File "json\__init__.py", line 238, in dumps
```

### 根因

`api/routers/data.py` 预览 Excel 时用：
```python
rows = df.where(pd.notnull(df), None).to_dict(orient='records')
```
**这个转换不可靠**：当整列为 `float64` 数值列（如 `video_url` 全空）时，填入的 `None` 会被
pandas 重新转回 `NaN`。结果 `rows` 里仍是 `float('nan')`。
FastAPI/Starlette 用标准 `json.dumps(allow_nan=False)` 序列化 → 遇到 NaN 直接抛
`ValueError`，接口返回 500。

**已用真实数据复现**：`xhs_search_20260916_160049.xlsx` 的 Contents 表 `video_url` 列 20 行全
为 NaN，转换后仍残留 20 个 float-nan → `json.dumps(allow_nan=False)` 崩溃。

### 修复

1. `api/routers/data.py`：新增 `sanitize_json_value()`，递归把 NaN/±Inf 转成 None，Excel 预览
   分支对每行做清洗。验证：清洗后 `video_url` 变为 `None`，序列化成功。
2. `api/main.py`：新增 `SafeJSONResponse`（重写 `render`，标准序列化失败时先清洗再序列化），
   并设为 FastAPI 的 `default_response_class`，全局防御 NaN 导致的 500。

## 问题二：子评论失败被误报为 ERROR

### 现象

运行日志反复出现 ERROR 级：
```
[XiaoHongShuClient.get_comments_all_sub_comments] Unexpected error when getting sub-comments
for note_id: ..., root_comment_id: ..., error: RetryError[<Future ... raised DataFetchError>]
```

### 根因

`get_note_sub_comments` 走 `client.request()`，该函数带 `@retry(stop_after_attempt(3))`。
当子评论接口返回业务错误（`success=False`）时抛 `DataFetchError`，重试 3 次仍失败后，
tenacity 抛出 **`RetryError`**（包裹 `DataFetchError`）。
而 `get_comments_all_sub_comments` 只捕获了 `DataFetchError`，**捕获不到 `RetryError`**，
于是落到 `except Exception`，被打成 ERROR「Unexpected error」。

本质上是**正常的“该评论无子评论 / 接口返回错误 → 跳过”场景**，不该报 ERROR，
且原逻辑会打断该评论剩余的子评论分页。

### 修复

`media_platform/xhs/client.py`：在 `get_comments_all_sub_comments` 中新增
`except RetryError as e:` 分支（位于 `except DataFetchError` 之后、`except Exception` 之前），
按“跳过该评论子评论”处理并降级为 WARNING。

### 说明

该错误**不影响主流程**——一级评论本身仍正常存入 Excel（日志中 `Stored comment to Excel` 正常）。

# 抖音登录修复记录（2026-09-16 晚）

## 问题现象

抖音平台采集启动后报错：
```
File "media_platform\douyin\login.py", line 121, in popup_login_dialog
playwright._impl._errors.TimeoutError: Locator.click: Timeout 30000ms exceeded.
- waiting for locator("//p[text() = '登录']")
```

## 根因

`popup_login_dialog` 原实现：
1. 先等旧容器 `//div[@id='login-panel-new']` 10 秒；
2. 等不到就直接 `locator("//p[text() = '登录']").click()`。

问题在于：抖音首页右上角「登录」按钮位于 `<pace-island>` 岛式容器内，当页面弹窗/遮罩存在
时，Playwright 的 actionability 检查（元素被遮挡、不接收指针事件）会让 `click()` **一直等待
直到 30 秒超时**，而不是直接失败。这导致登录流程直接崩掉。

（实测：`//p[text() = '登录']` 元素真实存在且可见，但默认 click 的等待策略会在被遮挡时卡死。）

## 修复

`media_platform/douyin/login.py`：

1. **`popup_login_dialog` 重写**：
   - 用多个候选选择器探测登录弹窗是否已出现（新旧 id 兼容）；
   - 「登录」按钮定位用多重文案选择器（`p`/`span`/`button`/`div` 的「登录」）；
   - 点击采用三级兜底：普通 `click(timeout=3000)` → `click(force=True)` → JS `el.click()`；
   - 每步短超时，避免再次卡 30 秒；全程日志输出，失败不抛异常。
2. **`login_by_qrcode` 增强**：二维码选择器改为多候选（`animate_qrcode_container` /
   含 `qrcode` 的 id/class / `canvas`），循环最多等 5 秒并尝试自动切回「扫码登录」tab，
   避免因改版直接 `sys.exit()`。

## 验证

源码模式实测（CDP 启动真实 Chrome 打开 www.douyin.com）：
```
[DouYinLogin.popup_login_dialog] login dialog box popped up automatically
popup_login_dialog 耗时 20.2s, 异常=None   ← 不再抛超时
登录弹窗 #login-panel-new 可见: True
```
